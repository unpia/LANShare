# Модель жизненного цикла проекта

**Проект:** LANShare — локальный файлообменник для Windows
**Команда:** 4 участника | **Срок:** 4 дня | **Документ:** версия 1.0

---

## 1. Выбранная модель: итеративная разработка с элементами Kanban

Проект выполняется **4 дня командой из 4 человек**. Выбрана итеративная модель:
4 итерации по 1 дню, каждая завершается работающим инкрементом продукта.

Дополнительно используются элементы **Kanban**:

* единая доска задач с колонками `Backlog → In Progress → Review → Done`;
* WIP-лимит: не более 2 задач в колонке `In Progress` на участника;
* ежедневный стендап 10 минут (что сделано / что мешает / что дальше);
* непрерывный поток задач без жёстких «заморозок» требований между итерациями.

## 2. Почему не Waterfall (каскадная модель)

| Аргумент | Пояснение |
|---|---|
| **Критические риски нужно снимать в первый день** | Два главных риска — работоспособность собственного сетевого протокола (UDP-поиск + TCP-передача) и упаковка `customtkinter` в один `.exe`. При каскадной модели проверка сборки попала бы в самый конец, и её провал обнулил бы всю работу. При итеративной модели «hello world»-сборка `.exe` проверяется уже в 1-й день. |
| **Требования уточняются по ходу** | Решение о передаче папок не было окончательным: сначала предполагалась рекурсивная передача файлов по одному, но по результатам итерации 3 (проверка на большом количестве мелких файлов) выбрана авто-архивация в `ZIP_STORED`. Waterfall не допускает таких разворотов без полного пересмотра ТЗ. |
| **Короткий срок** | 4 дня не позволяют выделить отдельные длинные фазы анализа, проектирования, реализации и приёмки. Итерации по 1 дню дают измеримый прогресс каждый день. |
| **Ранняя демонстрация** | После каждой итерации есть работоспособный сценарий для показа: 1-й день — каркас и сборка, 2-й — обнаружение устройств, 3-й — передача файлов, 4-й — диалоги, история и релиз. |
| **Параллельная работа 4 участников** | Модульная структура (`network/`, `ui/`, `utils/`) позволяет участникам работать параллельно; при этом за счёт интеграции в конце каждой итерации расхождения выявляются сразу, а не на финальной сборке. |
| **Обратная связь как критерий готовности** | «Готово» означает работающий сценарий, проверенный на стенде, а не написанный документ. |

**Ограничения модели и их компенсация:**

* риск «расползания» объёма работ → WIP-лимит и правило «новая функция только вместо другой, а не в дополнение»;
* риск неполной документации → документация пишется внутри итераций (ТЗ — день 1, отчёт по тестированию — день 4), а не «потом»;
* риск незавершённого инкремента к концу дня → критерий готовности (DoD) ниже.

## 4. Правила работы (Kanban + DoD)

**Критерий готовности задачи (Definition of Done):**

1. код компилируется, приложение запускается;
2. сценарий проверен вручную или автотестом, результат записан в [docs/Testing.md](Testing.md);
3. изменения внесены в журнал изменений [docs/Project_Management.md](Project_Management.md);
4. документация (ТЗ/инструкция) обновлена, если поведение изменилось.

**Правила доски:**

* задача берётся в работу только при свободном WIP-слоте (≤ 2 на участника);
* задача не переходит в `Done` без проверки вторым участником (Review);
* выявленный на Review дефект возвращается в `In Progress` с пометкой причины.

## 5. Итоги применения модели

| Принцип | Как проявился в проекте |
|---|---|
| Ранняя проверка рисков | Сборка `.exe` проверена в 1-й день, а не в последний |
| Готовность к изменениям | Рекурсивная передача папок заменена на `ZIP_STORED`-архивацию в 3-й итерации |
| Непрерывный поток задач | 4 итерации без «заморозок», задачи добирались из `Backlog` по мере освобождения |
| Работающий инкремент каждый день | 4 демонстрируемых состояния продукта |
| Документирование внутри процесса | ТЗ — день 1, ЖЦ — день 2, управление — день 3, тестирование и инструкция — день 4 |
